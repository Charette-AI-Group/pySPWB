# Contributing to pySPWB

Thanks for looking. This is a port of a LabVIEW application, and a few of
its rules are unusual — worth reading before your first change.

## Setup

```bash
pip install -e ".[dev]"
pytest
```

The GUI tests run offscreen (`QT_QPA_PLATFORM=offscreen`), so no display is
needed.

## The two rules that are not negotiable

### 1. `spwb.processing` must never import Qt

The package is split so that a notebook user can `pip install spwb` and get
the DSP and file IO without the GUI stack:

```
src/spwb/
├── processing/   Qt-free by contract
└── gui/          the only package that may import Qt
```

`tests/test_separation.py` enforces this: it imports every processing
module in a clean subprocess and fails if Qt gets loaded, greps the
processing sources for Qt names, and runs a full analysis with Qt made
unimportable. If you need Qt for something, it belongs in `spwb/gui`.

The dependency arrow is one-way: `gui` imports `processing`, never the
reverse.

### 2. Numerical behaviour is pinned to LabVIEW

The DSP is not "a reasonable implementation of a spectrum" — it reproduces
what the original application computed, so that results carried over from
LabVIEW still match. `tests/fixtures/*.npz` hold data generated by driving
**LabVIEW 2022 itself** over COM.

If you change anything in `processing/dsp`, the fixture tests must still
pass. If you believe a fixture is wrong, say so in the PR with your
reasoning — do not regenerate it silently.

Regenerating fixtures needs LabVIEW 2022 + pywin32 on Windows:

```bash
python tools/make_fixtures.py            # windows and spectra
python tools/make_raw_window_fixtures.py # raw window shapes
python tools/make_tf_fixtures.py         # cross spectra
python tools/make_stft_fixtures.py       # spectrograms
```

Most contributors will never need to run these. The fixtures are committed.

## Style

Match the surrounding code. Notably:

* **Docstrings name their source VI.** Every ported module says which
  LabVIEW block diagram it came from. Keep that link — it is how the next
  person checks your work against the original.
* **Comment the non-obvious conventions, not the code.** `# NI's gaussian
  is symmetric over n+1 points truncated to n` earns its place; `# loop
  over channels` does not.
* Tests are named after the behaviour they pin, and assert real numbers
  (a sine of amplitude A reads A/√2) rather than "runs without error".

## Reporting a numerical difference

If pySPWB disagrees with the LabVIEW application on real data, that is the
most valuable bug report this project can get. Please include:

* the input (a small TDMS or WAV if you can share one),
* the settings used in both (block size, window, overlap, function type),
* both results.

Known deliberate differences are listed in the README under
"Numerical fidelity" — check there first.
